# Concurrency and lifecycle

The implementation has a single-owner execution model. The server enforces serial **storage calls** for its own store through one executor. Embedded callers can invoke the synchronous façade directly. The façade and engine do not lock operations or claim an isolation level. Correct use requires serializing reads, writes, rollover and close, keeping input arrays stable during calls, and granting one instance exclusive access to its directory. ## Who owns which boundary?

| State or resource | Actual owner and coordination |
| --- | --- |
| Active reference, immutable deque, factory counter | `HashIndexEngine` and its factory mutate ordinary fields and an `ArrayDeque`. Switching active and publishing the old immutable takes two updates. Concurrent reads can observe an inconsistent layout. |
| Per-segment key state | The segment reader and mutable writer share `HashIndex`. Its map and set and the two-step transitions lack synchronization. Older indexes are only read through the normal engine path after construction. |
| File position and record contents | `RecordWriter` queries the file size, positions the write channel at that offset and transfers the record. Two writers can observe the same size, and a sequence of short writes has no engine-level mutual exclusion. The value array is read twice during encoding. |
| Segment read channels | A read uses positional I/O, so it need not change a shared cursor. That fact alone cannot protect an index lookup or pin the channel between lookup and use. Rollover and close can close a reader's handle. |
| Server request execution | A single worker executes queued reads, mutations and response callbacks. This serializes those requests against each other. It gives no coordination with another store, external file access, or embedded calls on another thread. [Server architecture](server-architecture.md) |

Two instances can successfully open the same existing active file and reconstruct independent indexes. A write through one need never become visible through the other's index. As either rolls over, the other can continue appending to a file its peer considers sealed. Reopening orders by filename ID, so a later append to an older ID may lose to an earlier append to a newer ID. `Files.createFile` detects a collision when creating the same pathname, but it provides no ownership over existing files or coherent lookup across instances. ## Acquisition, close and use after failure

The following sequence describes observable transitions. There is no lifecycle enum or closed/failed flag.

1. `KeyValueStore` constructs the engine synchronously. The loader accumulates immutable objects and opens the mutable last. Constructors own partially acquired channel handles. On the caught open and replay-I/O failures they attempt cleanup, and the loader closes completed immutables. A direct corruption or other unchecked failure outside those catches can abandon the current handles and previous objects. Retrying construction can increase descriptor pressure until the runtime releases them. [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java) · [ImmutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/ImmutableSegment.java) · [SegmentLoader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/loader/SegmentLoader.java)
2. A healthy instance accepts any validated call. When append or force reports an error the active file is still attached, so the next call can read the old index or write again. There is no automatic rollback, tail validation or fence that prevents further successful acknowledgments behind damaged bytes. A failed rollover normally leaves the previous layout installed. [Failure windows](durability-and-recovery.md)
3. `HashIndexEngine.close` first calls `mutableSegment.sync()`. A `SegmentIOException` is saved as a `StorageEngineException`. It then calls `mutableSegment.close()` (read channel, then write channel) and closes each immutable read channel. Finally it throws the saved exception, if any. Both segment close methods catch individual channel-close `IOException`s, log warnings and continue. [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java) · [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java) · [ImmutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/ImmutableSegment.java)
4. `StorageEngine.close` says the instance must not be used after any close attempt and requires reporting failure to release resources. The implementation relies on the caller to observe that terminal state. A miss or indexed tombstone can still return absence without channel I/O. A present lookup or a mutation generally fails against a closed channel. A second close normally encounters a failed force on the closed appender. A close I/O error alone can be hidden from the caller, contrary to the reporting contract. [StorageEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/StorageEngine.java) · [SegmentReader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/SegmentReader.java)

**Why changing the map alone is insufficient.** A reader could capture the old active segment while rollover is rebuilding it and use its read channel after the writer closes it. A different interleaving exposes the new empty active before the old segment has entered the deque. Both races concern ownership and publication of the entire layout, even if each index operation were thread-safe. These are source-derived risks outside the serialized calling convention.

## Architectural alternatives

- An internal lock or single engine-owned worker covering complete operations, including open/close transitions and rollover, could make safety independent of the entry point. A lock adds contention around I/O. An asynchronous worker adds a queue and an ownership decision for pending calls. External serialization keeps the present embedded path simple when one caller already owns it.
- Explicit opening, open, failed and closed states could reject new work after uncertain writes and give uniform post-close behavior. Scoped acquisition with cleanup on *every* exceptional exit could cover corrupt rebuilds. Preserving the primary cause while reporting secondary cleanup failures would make the close contract observable.
- An exclusive directory lock held from before discovery until final release could reject overlapping instances on supported filesystems. This requires clear lock semantics across processes and providers. It does not prevent an uncooperative process from editing files.
- Concurrent reads with a serialized writer require a consistent view of both the active index and segment ordering, plus a way to keep channels alive until in-flight reads finish. Recovery needs a stable file set. Future compaction would also need to defer reclamation while any reader can still reach the old files. [Indexing](indexing.md) · [Segment management](segment-management.md)

**Open question.** Is single-owner use a caller obligation intended for the embedded API, or a condition the engine should enforce? That decision determines where synchronization, directory ownership and failed-state reporting belong.
