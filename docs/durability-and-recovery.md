# Durability and recovery

ShaleDB persists the append history. On open it accepts every complete record the reader validates, including one whose caller never received success. It has no commit marker, undo log, persisted index, checkpoint, tail repair or alternate replica. The disk record, the in-memory visibility of its effect and the caller's acknowledgment are three distinct events. [RecordWriter](../storage/src/main/java/com/ryszardzmija/shaledb/storage/serialization/io/RecordWriter.java) · [SegmentWriter](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/SegmentWriter.java) · [IndexBuilder](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/index/IndexBuilder.java)

## Boundaries on the success path

| Event | What has happened when it returns |
| --- | --- |
| Create file | `Files.createFile` has created the name. The factory returns the path only after `forceDirectory(segmentDir)` succeeds. The server may just have created the directory hierarchy with `Files.createDirectories`. It does not also force each new directory's entry in its parent. |
| Write record | `RecordWriter.write` has submitted the entire byte buffer through the append channel and returned its initial position. File content may still be cached. The engine has yet to change the index. |
| Force file | `SYNC_EACH_WRITE` is the only defined mode. `forceFile` calls `FileChannel.force(true)` on the append channel, requesting persistence of contents and metadata. Success is the engine's durability boundary for that mutation, conditional on the storage stack honoring the call. |
| Publish and return | `SegmentWriter` records the new offset or deleted marker in memory. The engine then queries size and may roll over. A normal embedded return follows. A remote client must additionally receive a successful RPC completion. |
| Close and reopen | Close attempts another force of the active file, then closes active and immutable channels. Reopen uses filename ordering and full replay. The engine writes no clean-shutdown marker. A complete compatible history yields the same map after an ordinary reopen. |

The policy comment explicitly favors correctness over throughput. It gives one force per mutation, plus the additional old-file force during rollover and the active-file force on close. The creation barrier covers the segment's entry in its directory. The append barrier covers the segment file. The paths to both are visible in [FileSystemSync](../storage/src/main/java/com/ryszardzmija/shaledb/storage/durability/FileSystemSync.java), [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) and [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java).

## Failure windows

The table follows **one serialized mutation** with an initially readable history, compatible settings, exclusive directory ownership and a functioning filesystem unless the row says otherwise. Bytes visible through a file channel can still be in volatile cache. Physical survival depends on the failure class below. An earlier acknowledged record can remain intact yet become unavailable because open requires *every* segment to replay successfully.

| Point of failure | Possible file and live index state | Caller and continued use | Next open and effect on earlier acknowledgments |
| --- | --- | --- | --- |
| Before the first byte is appended | Log and index retain the previous state. Examples include ordinary argument rejection or failure to obtain the channel position. | The call fails. An argument correction is safe. An I/O failure may require restoring access. | No new record to replay. Earlier records remain available under the initial assumptions. |
| During header or payload write | The file may contain zero bytes of the record, a prefix, or bytes whose completion the caller cannot establish. The index update and force are skipped on a write exception. | I/O error. The engine still permits further appends. Following a partial record with another append can turn a bad tail into a bad interior record. Continuing writes is unsafe for replay. | No new bytes gives the old state. A complete valid record takes effect. A short or invalid record stops open, potentially hiding earlier and later acknowledged data. |
| After complete append, before force | A full record reached the channel. The old index still applies. On a crash the record's survival is uncertain. | Loss of the process gives the caller no reliable acknowledgment. The normal live call would next force. | A surviving valid record takes effect. A missing record leaves old state. An invalid surviving tail blocks startup. Earlier forced data can become inaccessible in the last case. |
| Force reports failure | The file can contain the full append. Persistence is unknown. The index retains the prior value or marker. | `StorageEngineException` on the normal mutation I/O path. A live get may still see old state. Later writes and close can force those same bytes. There is no fail-stop transition. | A complete surviving append is replayed, including a delete. A previously acknowledged value can then be superseded by a mutation that reported failure. Prior bytes may still exist. |
| After successful force, before publication | Complete forced record under the storage assumptions. Live index is still old, or publication was interrupted. | A process exit loses the reply. If an in-process unchecked failure interrupts a map/set transition, continued consistency is unestablished. | Rebuild derives the new state from the record, even without an acknowledgment. Earlier acknowledged state changes only through normal key supersession under the assumptions. |
| After publication, before acknowledgment | Bytes have been forced and the index contains the mutation. A failed size query can escape after this point. A failed response can occur still later. | The next serialized reader may see the new state despite the error, timeout or missing reply. A transport failure alone leaves the store usable. A storage error needs independent diagnosis. | Compatible, intact files replay the mutation. Retrying can append another record and supersede an intervening update. |
| During creation or rollover | The triggering record is already forced and indexed when rollover begins. The old segment is still live before the handoff. A new empty higher-ID file may exist even when the handoff failed. | The engine catches `RolloverException`, logs a warning and returns success. Repeated appends to the old file can produce unreadable offsets. Unwrapped corruption during conversion instead fails the call and can leak resources. | Discovery picks the highest surviving ID. An empty successor by itself leaves older values readable. Bad records abort replay. A missing file can silently remove acknowledged history. [Segment management](segment-management.md) |
| During startup or replay | Earlier files may have been opened and partly or completely indexed in memory. Replay reads the history without rewriting it. Empty-directory initialization can create the first segment. | No engine is returned on failed load. Some exception paths release channels, others bypass cleanup. A cause such as temporary I/O or incompatible settings can persist across attempts. | Another open starts again at offset zero in each file. Deterministically invalid bytes fail again. Intact older data is inaccessible through the store until the cause is resolved. |
| During close | A failed final force leaves any previously uncertain bytes uncertain. The engine attempts channel release even after that force failure. | A final force error is reported after cleanup. Channel close I/O errors alone are logged. The contract ends use of the instance either way. | Reopen judges the actual surviving files. A final force error alone does not establish that earlier individually forced records were lost. [Lifecycle](concurrency-and-lifecycle.md) |

## What the environment can invalidate

| Event | Recovery implications |
| --- | --- |
| Normal shutdown and reopen | With complete writer/reader-compatible history, stable names and exclusive access, reconstruction replays the same logical order. A clean shutdown cannot make an oversized record acceptable or repair an already malformed tail. |
| Unexpected process termination | JVM indexes and channels are lost. The OS and its page cache may survive, so even an unforced complete record may be visible to a new process. No shutdown hook or close is required to make an already forced record replayable. |
| Operating-system crash | Volatile OS cache can be lost. Survival of previously forced file data and necessary directory entries depends on the local filesystem's persistence semantics. A write in progress has no whole-record atomicity guarantee. |
| Power loss | Filesystem guarantees additionally depend on controller/device cache flushes and write ordering surviving loss of power. The code cannot observe whether a device honored a successful force. Unforced writes and newly created ancestors are uncertain. |
| Filesystem or device failure | Open, append, force, read and cleanup may independently fail. Neither another force nor a new process guarantees recovery. Damage can affect previously acknowledged records or the directory itself. |
| Arbitrary persistent corruption | Types, lengths and CRCs catch many damaged records during replay or a present lookup. A whole missing segment, clean truncation at a record boundary, or replacement by a complete valid record can escape all record checks. A CRC is neither an inventory nor an authenticity check. |

The implementation assumes a provider that supports append channels, coherent positional reads from a second handle, and opening and forcing a directory. It also assumes durable directory ancestry, stable filenames and a storage stack with meaningful force semantics. The repository's real-file tests exercise the test host. They provide no power-cut or device-failure evidence. [Testing](testing.md)

## Recovery policy and uncertainty

The reader reports unexpected EOF, invalid type/length and checksum mismatch as corruption. Replay stops at the first error encountered in load order. It does not serve a verified prefix, skip unreadable history or truncate any file. Stopping preserves evidence and prevents an older value from reappearing because a newer tombstone was skipped. The cost is that a single bad record can deny access to unrelated keys in healthy files. [RecordReader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/serialization/io/RecordReader.java) · [IndexBuilder](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/index/IndexBuilder.java) · [SegmentLoader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/loader/SegmentLoader.java)

An explicitly recognized short final record in the **active** segment could justify a conservative tail-recovery policy if the intended crash model permits losing that suffix. A short read could also follow damage to a formerly acknowledged record. A CRC mismatch, an invalid interior record, or an unexpectedly short immutable file supplies still less basis for discarding history. A policy that preserves the original evidence and distinguishes these cases limits accidental loss. Even a prefix scan cannot detect records or files missing at clean boundaries without independent metadata.

A failed append or force could put an instance into a failed state and surface an explicit *outcome unknown* error. This would prevent later acknowledgments behind a broken tail at the cost of availability until reopening or inspection. File-set metadata could make missing files detectable, at the cost of another durable update protocol. **Open questions** include which failures the project promises to survive and what evidence is sufficient to discard a suffix. Neither a clean reopen nor a successful force on one host resolves those policy choices.
