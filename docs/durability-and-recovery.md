# Durability and recovery

ShaleDB persists the append history. On open it accepts every complete record the reader validates, including one whose caller never received success. It has no commit marker, undo log, persisted index, checkpoint, tail repair or alternate replica. The disk record, the in-memory visibility of its effect and the caller's acknowledgment are three distinct events. [RecordWriter](../storage/src/main/java/com/ryszardzmija/shaledb/storage/serialization/io/RecordWriter.java) · [SegmentWriter](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/SegmentWriter.java) · [IndexBuilder](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/index/IndexBuilder.java)

## Boundaries on the success path

| Event | What has happened when it returns |
| --- | --- |
| Create file | An atomic create-new open has reserved the name. The factory has forced the new file's contents and metadata, closed its channel and forced the directory containing the file. When the server creates a new directory hierarchy, durability of the new ancestors requires separate synchronization. |
| Write record | `RecordWriter.write` has transferred the entire byte buffer and returned the starting offset and encoded size. File content may still be cached. Force and index publication follow the transfer. |
| Force file | `SYNC_EACH_WRITE` is the only defined mode. `forceFile` calls `FileChannel.force(true)` on the append channel, requesting persistence of contents and metadata. Success is the engine's durability boundary for that mutation, conditional on the storage stack honoring the call. |
| Publish and return | `SegmentWriter` records the new offset or deleted marker in memory. The engine then queries size and may roll over. A normal embedded return follows. A remote client must additionally receive a successful RPC completion. |
| Close and reopen | Close from `OPEN` attempts another force of the active file. Close from `FAILED` begins directly with channel cleanup. Ownership release follows channel cleanup. Reopen acquires ownership before validating the layout, ordering files by numeric ID and replaying them. A complete compatible history yields the same map after an ordinary reopen. |

The policy requires one force per mutation, an additional old-file force during rollover, and the active-file force when closing an operational engine. Initial and rollover creation each require their own file force followed by a directory force. Segment publication assumes that the configured directory and its ancestors are already durable. [FileSystemSync](../storage/src/main/java/com/ryszardzmija/shaledb/storage/durability/FileSystemSync.java) · [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

The `LOCK` file provides runtime coordination and carries no recovery metadata. Ownership requires no force on that file. Segment publication retains its file and directory barriers. [Concurrency and lifecycle](concurrency-and-lifecycle.md)

## Failure windows

The table follows **one serialized mutation** with an initially readable history, compatible settings, exclusive directory ownership and a functioning filesystem unless the row says otherwise. Bytes visible through a file channel can still be in volatile cache. Physical survival depends on the failure class below. An earlier acknowledged record can remain intact yet become unavailable because open requires *every* segment to replay successfully.

| Point of failure | Possible file and live index state | Caller and continued use | Next open and effect on earlier acknowledgments |
| --- | --- | --- | --- |
| Before the first byte is appended | Log and index retain the previous state. Examples include ordinary argument rejection, failure to query file size or failure to position at EOF. | The call fails. An argument correction is safe. An I/O failure may require restoring access. | No new record to replay. Earlier records remain available under the initial assumptions. |
| During header or payload write | The file may contain zero bytes of the record, a prefix, or bytes whose completion the caller cannot establish. The index update and force are skipped on a write exception. | I/O error. The engine still permits further appends. Following a partial record with another append can turn a bad tail into a bad interior record. Continuing writes is unsafe for replay. | No new bytes gives the old state. A complete valid record takes effect. A short or invalid record stops open, potentially hiding earlier and later acknowledged data. |
| After complete append, before force | A full record reached the channel. The old index still applies. On a crash the record's survival is uncertain. | Loss of the process gives the caller no reliable acknowledgment. The normal live call would next force. | A surviving valid record takes effect. A missing record leaves old state. An invalid surviving tail blocks startup. Earlier forced data can become inaccessible in the last case. |
| Force reports failure | The file can contain the full append. Persistence is unknown. The index retains the prior value or marker. | `StorageEngineException` on the normal mutation I/O path. This error currently leaves the engine `OPEN`. A live get may still see old state, and later writes or close can force those same bytes. | A complete surviving append is replayed, including a delete. A previously acknowledged value can then be superseded by a mutation that reported failure. Prior bytes may still exist. |
| After successful force, before publication | Complete forced record under the storage assumptions. Live index is still old, or publication was interrupted. | A process exit loses the reply. If an in-process unchecked failure interrupts a map/set transition, continued consistency is unestablished. | Rebuild derives the new state from the record, even without an acknowledgment. Earlier acknowledged state changes only through normal key supersession under the assumptions. |
| After publication, before acknowledgment | Bytes have been forced and the index contains the mutation. A failed size query can escape after this point. A failed response can occur still later. | The next serialized reader may see the new state despite the error, timeout or missing reply. A transport failure alone leaves the store usable. A storage error needs independent diagnosis. | Compatible, intact files replay the mutation. Retrying can append another record and supersede an intervening update. |
| During creation or rollover | The triggering record is already forced and indexed when rollover begins. A new empty higher-ID file may exist even when the handoff failed. | An operational size or handoff failure reports `FORCE_COMPLETED`. An error after active retirement begins moves the engine to `FAILED`. [Segment management](segment-management.md) | Discovery picks the highest surviving ID. An empty successor by itself leaves older values readable. Bad records abort replay. A missing file can silently remove acknowledged history. |
| During startup or replay | Earlier files may have been opened and partly or completely indexed in memory. Replay reads the history without rewriting it. Empty-directory initialization can create the first segment. | A failed load returns no engine. Expected open and replay failures trigger channel cleanup. A cause such as temporary I/O or incompatible settings can persist across attempts. | Another open starts again at offset zero in each file. Deterministically invalid bytes fail again. Intact older data is inaccessible through the store until the cause is resolved. |
| During close | A failed final force leaves any previously uncertain bytes uncertain. The engine attempts channel release after that force failure. | A force or channel close failure reaches the caller. The first failure remains primary, with later cleanup failures suppressed. [Lifecycle](concurrency-and-lifecycle.md) | Reopen judges the actual surviving files. A final force error alone does not establish that earlier individually forced records were lost. |

## What the environment can invalidate

| Event | Recovery implications |
| --- | --- |
| Normal shutdown and reopen | With complete writer/reader-compatible history, stable names and exclusive access, reconstruction replays the same logical order. A clean shutdown cannot make an oversized record acceptable or repair an already malformed tail. |
| Unexpected process termination | The OS releases the file lock and leaves the `LOCK` entry available to reuse. JVM indexes are lost. The OS and its page cache may survive, so even an unforced complete record may be visible to the next owner. Replay still requires a complete, compatible segment history. |
| Operating-system crash | Volatile OS cache can be lost. Survival of previously forced file data and necessary directory entries depends on the local filesystem's persistence semantics. A write in progress has no whole-record atomicity guarantee. |
| Power loss | Filesystem guarantees additionally depend on controller/device cache flushes and write ordering surviving loss of power. The code cannot observe whether a device honored a successful force. Unforced writes and newly created ancestors are uncertain. |
| Filesystem or device failure | Open, append, force, read and cleanup may independently fail. Neither another force nor a new process guarantees recovery. Damage can affect previously acknowledged records or the directory itself. |
| Arbitrary persistent corruption | Types, lengths and CRCs catch many damaged records during replay or a present lookup. Present lookups also detect valid records with the wrong key or type. A missing segment, clean truncation at a record boundary, or substitution of a valid normal record with the same key can still escape detection. |

The implementation assumes a provider that supports positioning the write channel at EOF, coherent positional reads from a second handle, and opening and forcing a directory. It also assumes durable directory ancestry, stable filenames and a storage stack with meaningful force semantics. The repository's real-file tests exercise the test host. They provide no power-cut or device-failure evidence. [Testing](testing.md)

## Recovery policy and uncertainty

Replay completes at EOF following a complete record or in an empty file. Applying that complete, valid history in append order reproduces the per-segment index states maintained by successful live mutations. A short header or payload causes `IncompleteRecordException`, and the scan retains it as the cause of the index-build failure. Invalid structure and CRC mismatch remain corruption. An incompatible payload budget and a stalled or failed channel transfer have their own diagnoses. Replay stops at the first failure in load order and leaves the segment bytes intact. One unreadable record can deny access to unrelated keys in healthy files. [Record format](record-format.md) · [IndexBuilder](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/index/IndexBuilder.java) · [SegmentLoader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/loader/SegmentLoader.java)

An incomplete record describes bytes that could not be obtained for an expected section. Interruption, damage to an acknowledged record and external modification can produce the same symptom. A future recovery policy could allow removal of a short final record in the **active** segment if the supported crash model permits losing that suffix. A CRC mismatch, an invalid interior record, or an unexpectedly short immutable file supplies still less basis for discarding history. Even a prefix scan cannot detect records or files missing at clean boundaries without independent metadata.

A failed append or force could put an instance into a failed state and surface an explicit *outcome unknown* error. This would prevent later acknowledgments behind a broken tail at the cost of availability until reopening or inspection. File-set metadata could make missing files detectable, at the cost of another durable update protocol. **Open questions** include which failures the project promises to survive and what evidence is sufficient to discard a suffix. Neither a clean reopen nor a successful force on one host resolves those policy choices.
