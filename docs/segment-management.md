# Segment management

One file accepts new records. Each older file is opened through a read-only segment object. The directory contains the only catalog. A file's numeric ID establishes its age, and its rank in the discovered set determines its role. There is no persisted seal, generation or expected file count. [FileFormatInfo](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/FileFormatInfo.java) · [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java)

## Discovery, creation and load order

1. The server creates the configured directory and missing parents. An embedded caller supplies an existing directory. The engine resolves its physical path and acquires exclusive ownership before accessing segments. [Application](../server/src/main/java/com/ryszardzmija/shaledb/server/Application.java) · [Concurrency and lifecycle](concurrency-and-lifecycle.md)
2. `SegmentFileDiscoverer` lists the directory's immediate children once, validates segment names and types, and returns paths in ascending ID order. Failure to open, iterate or close the stream fails discovery. [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java)
3. The engine uses the greatest discovered ID as both the active file's ID and the starting point for rollover allocation. If discovery found no segments, the factory creates ID 1. For each creation it allocates the next ID, opens the new canonical path with `WRITE` and `CREATE_NEW`, forces the file with `force(true)`, closes it, then forces the parent directory before returning the path. [SegmentLayout](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentLayout.java) · [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [FileSystemSync](../storage/src/main/java/com/ryszardzmija/shaledb/storage/durability/FileSystemSync.java)
4. `SegmentLoader` visits immutable paths in descending ID order, opens each with `READ`, rebuilds its index, and keeps the completed segments in a newest-first list. It opens the mutable last with separate `READ` and `WRITE` channels, replays that file, and gives its reader and writer the same index. Those opens require existing files. Empty segments replay to empty indexes. The loader transfers the complete layout to the engine only after every segment is ready. [SegmentLoader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/loader/SegmentLoader.java) · [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java) · [ImmutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/ImmutableSegment.java)

A healthy engine with `S` segments retains `S + 2` file channels. There is one reader per segment, one active appender and one ownership channel. Each append explicitly positions the write channel at the physical EOF. Rollover temporarily needs channels for both representations of the old file and the replacement active file. The same database lock stays held throughout rollover. External access to the files is outside the ownership protocol. [Record format](record-format.md) · [Concurrency and lifecycle](concurrency-and-lifecycle.md)

| Resource | Acquisition, borrowing and release |
| --- | --- |
| Active read and write channels | `MutableSegment` acquires and owns both. Index replay and the record reader borrow the read channel. The record writer borrows the write channel and passes it to the force helper. |
| Historical read channels | `ImmutableSegment` acquires and owns its read channel. Index replay and the record reader borrow it. Rollover constructs a separate read view of the retiring file. |
| Creation channel | `SegmentFileFactory` acquires and closes the temporary file channel before forcing the directory. The file force borrows it. |
| Discovery stream and directory force channel | The discovery and sync methods own these temporary read resources in their local scopes. |
| Segment channels still open after close errors | `SegmentChannelCleanup` takes responsibility from the acquisition or close scope. The engine retries them during close while `DatabaseLock` keeps them reachable and the directory owned. |

## Names and identifiers

New files use the case-sensitive name `segment_%019d.log` with 19 zero-padded ASCII decimal digits. The first is `segment_0000000000000000001.log`. The ID domain is 1 through `Long.MAX_VALUE`. Discovery accepts the positive ASCII decimal IDs prior readers accepted, including six-digit padding from the original writer. It also accepts historical localized names that use a single set of decimal digits representable as Java `char` values. These names must use either 19 digits or the original signed-int format's minimum width of six. The engine opens supported names in place. Mixed digit sets, signs, whitespace, nonpositive IDs and overflow fail validation. [FileFormatInfo](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/FileFormatInfo.java)

The lowercase prefix `segment_` reserves a directory entry for this format. A reserved entry with an invalid name or an unsupported type causes open to fail. Discovery requires regular files and inspects their metadata without following symbolic links. The dedicated `LOCK` entry, uppercase prefixes and other names outside the segment namespace are ignored by discovery. Two paths with the same numeric ID or with the same filesystem file key cause open to fail with both paths in the diagnostic. On providers that supply no file key, hard-linked segment aliases are unsupported and may go undetected. Invalid layouts remain intact for investigation. [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java) · [Storage semantics](storage-semantics.md#embedded-exception-contract)

## Rollover in execution order

The size policy reads `mutableSegment.size()` through the read channel **after** the mutation is forced and indexed. It triggers when actual file bytes are `>= maxSegmentSize`. Size includes headers and all old versions. Admission ensures an individual record fits the budget of an empty segment. The engine checks the segment's size only after append, and the constructor performs no size-triggered rollover. [Configuration](configuration.md) · [SizeBasedRolloverPolicy](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/SizeBasedRolloverPolicy.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

| Order | `RolloverHandler.rollOver` and engine publication |
| --- | --- |
| 1 | Allocate the next ID, create and force the empty file, then force its directory entry. |
| 2 | Construct a new mutable segment on the path, open its two channels and build its initially empty index. |
| 3 | Force the **old** mutable segment again. Open a separate read channel on its file and build a **new** immutable segment by rescanning that entire file. The existing mutable index is discarded on success. |
| 4 | Prepare the result, close the old mutable's two channels and transfer the pair of new segment objects to the engine. A channel-close failure fails the handoff. |
| 5 | The engine inserts the new immutable into its preallocated list and replaces its active reference. The just-written record now belongs to the newest immutable. |

This sequence preserves the old writer through creation and conversion failures handled before step 4. It also makes the triggering call pay for an extra force and replay proportional to the old file's length. Transferring a sealed segment's existing validated index could avoid that scan, at the cost of a more explicit channel and index ownership transfer. [RolloverHandler](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/RolloverHandler.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

## Invariants and failure paths

| Property | Enforcement, failure and consequence |
| --- | --- |
| Segment IDs are unique and chronological. | Discovery rejects duplicate IDs. The factory allocates after the greatest ID even when history has gaps. A failed attempt consumes its allocated ID for that instance. Reopen seeds allocation from the highest surviving ID. A database at `Long.MAX_VALUE` can open and read normally. A later request for a successor fails with `SEGMENT_ID_EXHAUSTED` before file creation. |
| Exactly one segment is logically writable. | Highest ID at open or the new active reference after rollover determines the writer. The file set and in-memory role switch are separate. A higher empty file left behind becomes the active file on reopen. This alone does not lose records in the previous file. |
| Present entries address complete records in the actual file. | Both indexed reads and replay use the file extent and applicable payload constraints. Lowering `maxSegmentSize` leaves valid historical offsets readable. A mutation on a full reopened active file can append beyond the threshold before the post-write rollover check runs. [SegmentReader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/SegmentReader.java) · [IndexBuilder](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/index/IndexBuilder.java) |
| One cooperating engine controls the file set. | The same exclusive directory lock covers discovery, startup and rollover. Atomic creation detects a pathname collision. Gaps are legal and discovery cannot detect missing files from IDs alone. [Concurrency and lifecycle](concurrency-and-lifecycle.md) |
| Acquired channels are released on operational failure. | Segment constructors attempt to close locally acquired channels after failed acquisition or replay. The loader attempts to close previously opened immutables on a segment failure. Secondary failures are suppressed on the primary cause chain. |

**Creation failure.** Atomic creation leaves any existing entry at the target path intact. If forcing or closing the new file fails, or the directory force fails, the factory attempts to delete only the file it just created and force the directory after deletion. Cleanup failures are suppressed on the primary cause. A file may survive if cleanup fails. If the directory force completes and closing the directory channel fails, creation reports an I/O failure and leaves the published file in place. A first file successfully created before a later loader failure can also remain. [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [Storage semantics](storage-semantics.md#embedded-exception-contract)

**Rollover failure.** The handler attempts to close both provisional segments and remove the successor file if creation returned its path. Cleanup also runs for unexpected exceptions, and secondary failures are suppressed. An operational size or handoff error reports `FORCE_COMPLETED`. Failure after retirement begins leaves the old active reference installed and moves the engine to `FAILED` until close. Safe persistent role transition remains open for M1.10. [Durability and recovery](durability-and-recovery.md)

## Reclamation and metadata

No operation reclaims history. Disk use, retained key copies, open channels and restart time can all grow while the logical map stays small. Compaction could select the latest surviving records, but dropping a tombstone is safe only when every older version it masks is also gone or otherwise excluded from lookup. New compacted files must preserve logical recency relative to still-live newer records. The current highest-ID rule would give a newly named copy precedence even if its contents were old.

A durable description of the active file set could distinguish a completed replacement from an orphan and permit detection of a missing expected file. It would introduce a second persistent object whose installation, directory force, crash recovery and retirement of old readers must agree. A future hard physical cap for new appends would need compatible definitions of record size, pre-append rotation and the oversized-single-record case.
