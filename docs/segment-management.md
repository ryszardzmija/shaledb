# Segment management

One file accepts new records. Each older file is opened through a read-only segment object. The directory contains the only catalog. A file's numeric ID establishes its age, and its rank in the discovered set determines its role. There is no persisted seal, generation or expected file count. [FileFormatInfo](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/FileFormatInfo.java) · [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java)

## Discovery, creation and load order

1. The server creates the configured directory and missing parents. An embedded caller supplies an existing directory. `SegmentFileFactory` checks `Files.isDirectory`, lists immediate entries matching `segment_\d+\.log`, parses IDs as Java `long` and remembers the maximum (zero if none). It does not test regular-file status. [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [Application](../server/src/main/java/com/ryszardzmija/shaledb/server/Application.java)
2. `SegmentFileDiscoverer` checks the directory and performs a **second** listing. It filters by the same full filename pattern, sorts by numeric ID ascending, designates the last path mutable and returns the rest in ascending order. If empty, it calls the factory for the initial mutable file. Unrelated names are ignored. [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java) · [SegmentLayout](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentLayout.java)
3. On creation the factory increments its in-memory counter *before* I/O, formats `segment_%019d.log`, and uses `Files.createFile` (fails if the path already exists). With ASCII decimal digits, the first generated name is `segment_0000000000000000001.log`. It forces the segment directory before returning the new path. Directory force opens a read channel on the directory, calls `force(true)` and closes the channel. [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [FileSystemSync](../storage/src/main/java/com/ryszardzmija/shaledb/storage/durability/FileSystemSync.java)
4. `SegmentLoader` iterates the immutable paths backwards, opening each with `READ`, rebuilding its index, and appending the object to the tail of a deque. The head is therefore the newest immutable. It opens the mutable last with separate `READ` and `WRITE` channels, replays that file, and gives its reader and writer the same index. Even an empty mutable goes through this machinery. The engine installs the completed pair. [SegmentLoader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/loader/SegmentLoader.java) · [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java) · [ImmutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/ImmutableSegment.java)

A healthy engine with `S` segments retains `S + 1` file channels (one reader per segment and one active appender). Each append explicitly positions the write channel at the physical EOF. This gives an empty or reopened segment the same append path and depends on serialized access and stable file ownership. Rollover temporarily needs channels for both representations of the old file and the replacement active file. An immutable segment is immutable by application convention. Another handle or process with filesystem permissions could still modify it. [Record format](record-format.md) · [Concurrency and lifecycle](concurrency-and-lifecycle.md)

## Rollover in execution order

The size policy reads `mutableSegment.size()` through the read channel **after** the mutation is forced and indexed. It triggers when actual file bytes are `>= maxSegmentSize`. Size includes headers and all old versions. Admission ensures an individual record fits the budget of an empty segment. The engine checks the segment's size only after append, and the constructor performs no size-triggered rollover. [Configuration](configuration.md) · [SizeBasedRolloverPolicy](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/SizeBasedRolloverPolicy.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

| Order | `RolloverHandler.rollOver` and engine publication |
| --- | --- |
| 1 | Allocate the next ID, create the empty file and force its directory entry. |
| 2 | Construct a new mutable segment on the path, open its two channels and build its initially empty index. |
| 3 | Force the **old** mutable segment again. Open a separate read channel on its file and build a **new** immutable segment by rescanning that entire file. The existing mutable index is discarded on success. |
| 4 | Close the old mutable's two channels and return the pair of new segment objects. The segment close methods log channel-close errors. |
| 5 | The engine first replaces its active reference, then inserts the new immutable at the head of its deque. The just-written record now belongs to the newest immutable. |

This sequence preserves the old writer through creation and conversion failures handled before step 4. It also makes the triggering call pay for an extra force and replay proportional to the old file's length. Transferring a sealed segment's existing validated index could avoid that scan, at the cost of a more explicit channel and index ownership transfer. [RolloverHandler](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/RolloverHandler.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

## Invariants and failure paths

| Property | Enforcement, failure and consequence |
| --- | --- |
| Segment IDs are unique and chronological. | For one factory, successful creates use increasing IDs. Failure consumes an ID in memory. A later process calculates its counter from surviving names, so gaps are legal and failed, absent IDs can be reused after restart. The read pattern allows differently padded names for the same number. Equal IDs have no specified recency tie-break, and over-range digits can raise an unwrapped parsing error. Incrementing `Long.MAX_VALUE` is unchecked. Unique representable IDs and an undisturbed directory are assumptions. |
| Exactly one segment is logically writable. | Highest ID at open or the new active reference after rollover determines the writer. The file set and in-memory role switch are separate. A higher empty file left behind becomes the active file on reopen. This alone does not lose records in the previous file. |
| Record starts are valid file offsets. | Under successful rollover and unchanged limits the start of the threshold-crossing record can still be below the threshold, even if its end overshoots. After rollover failure or reopening an already full active file, a later append can *start* at or above the threshold. It can be forced and indexed, then `SegmentReader.get` rejects a present hit there. Rebuild accepts the start because it scans to actual EOF. Lowering the setting has the same read-side effect. [SegmentReader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/SegmentReader.java) · [IndexBuilder](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/index/IndexBuilder.java) |
| One owner controls the file set. | The two startup listings, per-process ID counter and in-memory roles are uncoordinated. Files may disappear, alias an ID or change while open. No manifest can identify a missing segment by a gap alone. [Concurrency and lifecycle](concurrency-and-lifecycle.md) |
| Acquired channels are released on failure. | Segment constructors close locally acquired channels on `IOException` or `IndexBuildException`. The loader closes previously opened immutables on `SegmentIOException`. Direct `DataCorruptionException` bypasses both cleanup paths. A failed load can leave open resources without a store for the caller to close. |

**Filename compatibility defect.** Creation uses the JVM's default formatting locale, while the discovery regex accepts ASCII digits. In a Java 25 check with format locale `ar-EG-u-nu-arab`, formatting ID 1 produced Arabic-Indic digits and the discovery pattern did not match the name. In a directory containing only that file, a restart with the same locale can try to create ID 1 again and fail on the existing path. Restarting with ASCII formatting can instead initialize a separate visible history in the same directory. These restart consequences follow from discovery and exclusive creation. Locale-independent formatting would prevent new mismatches. Existing differently formatted names would still require an explicit policy for numeric-ID collisions. [File naming constants](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/FileFormatInfo.java)

**Creation failure.** A create I/O error becomes `SegmentFileException`. If directory force fails after creation, the factory attempts `deleteIfExists`, then forces the directory again. A cleanup failure is attached as suppressed to the durability cause. A surviving file or uncertain directory entry is possible. A first file successfully created before a later loader failure can also remain. Discovery and loading failures that are wrapped reach the façade as `StorageEngineException`. [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

**Rollover failure.** If old-file sync or opening its immutable view throws `SegmentIOException`, the handler closes the new mutable. For caught segment-file or segment-I/O errors it attempts deletion and directory force if it received a new path. Cleanup errors are logged. It throws `RolloverException`, which put/delete log as a warning after the mutation. The old active stays installed and later mutations retry the policy after appending again. A size-query exception occurs outside this handler. A direct corruption exception during immutable rebuild escapes the catch blocks, can leave the new file and channels behind, and reaches the caller after the old index was updated. [Durability and recovery](durability-and-recovery.md)

## Reclamation and metadata

No operation reclaims history. Disk use, retained key copies, open channels and restart time can all grow while the logical map stays small. Compaction could select the latest surviving records, but dropping a tombstone is safe only when every older version it masks is also gone or otherwise excluded from lookup. New compacted files must preserve logical recency relative to still-live newer records. The current highest-ID rule would give a newly named copy precedence even if its contents were old.

A durable description of the active file set could distinguish a completed replacement from an orphan and permit detection of a missing expected file. It would introduce a second persistent object whose installation, directory force, crash recovery and retirement of old readers must agree. An alternative for today's size mismatch is to validate indexed offsets against the physical file and record boundary while treating the rollover setting purely as policy. If a hard physical cap is intended, record size, pre-append rotation and the oversized-single-record case need compatible definitions. Which interpretation should govern existing files is open.
