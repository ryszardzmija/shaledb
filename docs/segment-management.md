# Segment management

The directory is the catalog. The segment with the greatest numeric ID is active and accepts appends. All lower IDs are historical and opened read-only. Gaps are legal. Without a manifest listing expected files, discovery cannot reliably detect a missing segment. [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java)

## Discovery and names

1. The server creates the configured directory and missing parents. An embedded caller supplies an existing directory. The engine resolves its physical path and acquires exclusive ownership before accessing segments. [Application](../server/src/main/java/com/ryszardzmija/shaledb/server/Application.java) · [Concurrency and lifecycle](concurrency-and-lifecycle.md)
2. `SegmentFileDiscoverer` lists the directory's immediate children once, validates segment names and types, and returns paths in ascending ID order. Failure to open, iterate or close the stream fails discovery. [SegmentFileDiscoverer](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileDiscoverer.java)
3. The engine uses the greatest discovered ID as both the active file's ID and the starting point for rollover allocation. If discovery found no segments, the factory creates ID 1. For each creation it allocates the next ID, opens the new canonical path with `WRITE` and `CREATE_NEW`, forces the file with `force(true)`, closes it, then forces the parent directory before returning the path. [SegmentLayout](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentLayout.java) · [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java) · [FileSystemSync](../storage/src/main/java/com/ryszardzmija/shaledb/storage/durability/FileSystemSync.java)
4. `SegmentLoader` visits immutable paths in descending ID order, opens each with `READ`, strictly rebuilds its index, and keeps the completed segments in a newest-first list. It opens the mutable segment last with separate `READ` and `WRITE` channels. The segment owns its replayed index and its physical reader and writer. Those opens require existing files. Empty segments replay to empty indexes. For a discovered active file, startup can recover an eligible incomplete tail through the existing write channel, then forces that file and the database directory. The loader transfers the layout after replay and the applicable publication barriers succeed. [Durability and recovery](durability-and-recovery.md) · [SegmentLoader](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/loader/SegmentLoader.java) · [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java) · [ImmutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/ImmutableSegment.java)

New names use `segment_%019d.log` with 19 zero-padded ASCII digits. IDs range from 1 through `Long.MAX_VALUE`. An empty layout starts with `segment_0000000000000000001.log`. Discovery accepts older ASCII decimal names with other padding and opens them in place. A localized name must use one decimal digit set representable in Java `char`s and either 19 digits or the legacy positive `int` width (at least six digits, padded only as needed). Signs, mixed digit sets, zero and overflow are invalid. Ordering is numeric across all accepted forms. [Filename rules](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/FileFormatInfo.java)

| Resource | Acquisition, borrowing and release |
| --- | --- |
| Active read and write channels | `MutableSegment` acquires and owns both. The scanner and record reader borrow the read channel. Recovery borrows the existing write channel to truncate an eligible suffix. The record writer borrows the write channel and passes it to the force helper. |
| Historical read channels | `ImmutableSegment` acquires and owns its read channel. The scanner and record reader borrow it. At rollover it receives the existing read channel, the segment reader and the local index from the retiring segment. |
| Creation channel | `SegmentFileFactory` acquires and closes the temporary file channel before forcing the directory. The file force borrows it. |
| Discovery stream and directory force channel | The discovery and sync methods own these temporary read resources in their local scopes. |
| Segment channels still open after close errors | `SegmentChannelCleanup` takes responsibility from the acquisition or close scope. The engine retries them during close while `DatabaseLock` keeps them reachable and the directory owned. |

The engine validates the incoming record before checking the active file's physical size. It counts the full encoded size, including the 13-byte header on every record. Every admitted record fits in an empty segment. The engine rolls over before appending if the active file already exceeds `maxSegmentSize` or the record is larger than the remaining capacity (`maxSegmentSize - currentSize`). Subtraction avoids overflow. An exact fit stays in the current file. [SizeBasedRolloverPolicy](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/SizeBasedRolloverPolicy.java)

The segment limit governs new appends. Reopening with a smaller limit preserves valid historical records and offsets beyond the new threshold. A full or oversized active file remains readable, and the next valid mutation requires rollover. [Configuration](configuration.md)

## Rollover sequence

1. The engine checks for a successor ID before retiring the old writer. Allocation starts after the greatest discovered ID and consumes one ID per creation attempt within the engine instance. Exhaustion leaves the store available for reads and mutations that still fit.
2. The engine closes the retiring writer and transfers its read channel and index to a historical view. Successful record and startup forces establish the durability of that segment before a higher ID can appear.
3. The factory creates the successor at its canonical name with `CREATE_NEW`, which preserves any colliding entry. It forces the empty file, closes the creation channel and forces the containing directory. The engine then opens the successor's read and write channels and initializes its index. Initial segment creation uses the same publication protocol.
4. The engine puts the historical view at the front of the history list, installs the successor as the sole active segment and appends the record there. Caller serialization and directory ownership keep readers out of the handoff. [RolloverHandler](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/RolloverHandler.java) · [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java)

On a failed publication, the factory attempts to remove only the segment it created and to force the directory after removal. A directory-channel close failure after a successful force leaves the published file in place. A later setup or handoff failure closes provisional resources under ownership. An empty successor that survives is a valid active segment on reopen. It has an empty index, so lookups continue into history. [Durability and recovery](durability-and-recovery.md) · [Concurrency and lifecycle](concurrency-and-lifecycle.md)

The policy reads the active file's physical size through its read channel. If that size exceeds the limit, a valid mutation requires a successor. Otherwise it compares the encoded size to `maxSegmentSize - currentSize`. Subtracting only within the limit avoids an overflowing sum. An exact fit appends to the current segment, and a later valid record that needs more space triggers rollover. Startup preserves complete records in a full or oversized active file. The existing physical extent still governs lookup and replay, including after a size-limit reduction. [SizeBasedRolloverPolicy](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/SizeBasedRolloverPolicy.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

| Order | Transition when the incoming record needs a successor |
| --- | --- |
| 1 | Preflight the next ID after the greatest allocated ID. Exhaustion returns `SEGMENT_ID_EXHAUSTED` before retirement, and reads and writes that fit remain available. Gaps are allowed. A creation attempt consumes its ID for that instance. |
| 2 | Retire the old writer and transfer its reader, read channel and local index to an immutable view. Successful prior appends already forced the file. Startup replay and publication cover a reopened active file. Fail-stop bars rollover following an ambiguous append. |
| 3 | Create the successor with `CREATE_NEW`, force the empty file and force its directory entry. Open the successor's read and write channels and initialize its empty index. |
| 4 | Insert the historical view at the front of the history list and install the successor as the sole active segment. Serialized entry points make these updates one observable transition. |
| 5 | Append the incoming record to the successor, force its file, publish the offset or tombstone, and return success. |

The old history's complete, forced state precedes the appearance of a higher ID. The existing segment reader continues to serve all older offsets. A successor contains only its own records, and the handler transfers the old index without reopening or rescanning the old file. The database lock spans the entire transition. [RolloverHandler](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/RolloverHandler.java) · [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java)

## Failure and cleanup

**Creation failure.** Atomic creation leaves an existing target intact. If forcing or closing the new file fails, or the directory force fails, the factory attempts to delete only the file it just created and force the directory after deletion. Cleanup failures are suppressed on the primary cause. A file may survive if cleanup fails. If the directory force completes and closing the directory channel fails, creation reports an I/O failure and leaves the published file in place. [SegmentFileFactory](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/files/SegmentFileFactory.java)

**Rollover failure.** The old writer's retirement is the first step that can change channel ownership. A size-query failure or a failure during retirement, creation, synchronization, initialization or in-memory handoff is terminal. A reported operational failure at these points has outcome `NOT_APPENDED`. The handler closes any provisional views it owns and preserves cleanup failures. After failed insertion into the history list, the engine closes the uninstalled reader and keeps the successor reachable for close. `SegmentChannelCleanup` tracks any channel still open after a failed close. A valid empty file returned by the factory stays in the directory if later setup fails. The highest surviving ID becomes active on reopen, including an empty successor. [Fail-stop policy](storage-semantics.md#fail-stop-policy) · [Durability and recovery](durability-and-recovery.md)

## Reclamation and metadata

No operation reclaims history. Disk use, retained key copies, open channels and restart time can all grow while the logical map stays small. Compaction could select the latest surviving records, but dropping a tombstone is safe only when every older version it masks is also gone or otherwise excluded from lookup. New compacted files must preserve logical recency relative to still-live newer records. The current highest-ID rule would give a newly named copy precedence even if its contents were old.

A durable description of the active file set could distinguish a completed replacement from an orphan and permit detection of a missing expected file. It would introduce a second persistent object whose installation, directory force, crash recovery and retirement of old readers must agree.
