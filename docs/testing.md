# Architectural verification

ShaleDB builds with Bazel 9.1.0 and Java language level 25. Bzlmod supplies Java, protobuf/gRPC generation and JUnit rules. JVM artifacts use pinned resolution and a checked-in lockfile. The storage and server `java_test_suite` targets glob their own test source trees and use the JUnit 5 runner. Assertions use AssertJ, with Mockito in the storage tests. The root `//:tests` aggregates both suites. ## Execution at the documented revision

| Bazel invocation | Observed result |
| --- | --- |
| `bazel test //storage:storage_tests` | All 8 targets passed (62 JUnit cases). |
| `bazel test //:tests` | All 10 targets passed (77 JUnit cases, including the same 62 storage cases and 15 server cases). |

Both runs used fresh test results, a temporary Bazel output location and an explicit Java 25 runtime path. The counts are from the Bazel results and JUnit XML. The suite exercised real local files and a loopback RPC server. Findings about untested failure windows, cross-segment replay, resource leaks and concurrent owners in this guide are from inspection of production code.

Two focused runtime observations supplement the suite. The production YAML loader mapped numeric `durabilityMode: 0` to `SYNC_EACH_WRITE`. Separately, the JDK 25 filename formatting and matching expressions used by the factory and discoverer disagreed under a locale with Arabic-Indic digits. The predicted restart consequences of that mismatch follow from the source. [Configuration](configuration.md) · [Segment management](segment-management.md)

## Properties with limited evidence

The central integration gap is **agreement between live and replayed state**. There is no engine-level test in this revision that forces several rollovers, overwrites and deletes keys across them, closes the store, rebuilds it and compares all logical results. Clean-restart preservation, cross-segment tombstone shadowing and the effects of changed size settings are consequently argued from the implementation. The correctness of the byte format and of the local publication ordering each has independent tests. [Indexing](indexing.md) · [Storage semantics](storage-semantics.md)

**Fault injection is local.** `SegmentWriter` accepts a record writer and index, and the file factory accepts a sync helper. At engine level, constructors directly open static `Files`/`FileChannel` resources, create fresh helpers and scan while acquiring them. Exercising, for example, successful creation followed by failed immutable replay or failed release of one channel is difficult to control from the public API. This is where a narrower construction/ownership boundary could improve testability. Multiple interfaces around straightforward pure computations would add little. [MutableSegment](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/model/MutableSegment.java) · [RolloverHandler](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/segment/rollover/RolloverHandler.java) · [HashIndexEngine](../storage/src/main/java/com/ryszardzmija/shaledb/storage/hash/HashIndexEngine.java)

## What different verification methods can establish

| Method | Architectural question it can answer |
| --- | --- |
| Real-file round trips plus independent binary fixtures | Does the current implementation read existing bytes and emit known bytes at nonzero offsets? Fixed vectors catch a reader and writer that drift together. They can also distinguish a canonical tombstone from a normal empty value. |
| Deterministic model-based comparison | With seeded operations and small rollover thresholds, does the public store agree with a binary-key reference map after each acknowledged operation and at clean reopens? Keeping the operation history explains the first mismatch across a segment boundary. |
| Controlled short I/O and failed barriers | Observing both the file prefix and index after failure distinguishes rejected, partially appended and fully appended but unacknowledged writes. An injected force exception alone cannot prove which bytes survived on real hardware. |
| Process-level crash observation | Termination at known append, force and publication boundaries, followed by a fresh opener, can establish replay behavior on the chosen filesystem. Killing a process leaves the OS cache alive. OS-crash or power-loss claims require observations at those separate boundaries and an explicit storage-stack model. |
| Controlled concurrency and lifecycle observation | Coordinating operations around index publication, rollover and close can expose stale layouts and released handles. Separate instances can exercise directory ownership. Server-level observations can distinguish queue admission, storage completion and client acknowledgment. The contract must specify which of those interleavings it supports. |

These methods answer different questions about the current interface and its assumptions. An open verification question is what the project considers a permissible recovered state after an unacknowledged operation. That choice determines the expected outcome of a crash observation.
